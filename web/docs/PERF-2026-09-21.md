# Where the open and the witness actually spend their time

2026-09-21. Today's live runs on this host showed **open/scan 25.8 s** and **witness
28.4 s**, against 2–3 s and 7 s in [M4-VERIFICATION.md](M4-VERIFICATION.md). The obvious
reading — "the gRPC-web gateways got slow and variable" — is measured here, and it is
**wrong**. The network is about **4%** of that time. The rest is the wasm doing arithmetic
on 777 more blocks than it used to.

Everything below was measured from this droplet (DigitalOcean, Linux) and from Playwright's
own chromium on the same droplet, against both gateways, five runs each, at two different
minutes. The harness speaks grpc-web by hand (5-byte frame headers over `fetch`) so that
what is timed is the wire and nothing else.

## 2. Is there a TLS handshake per call?

No. Chrome DevTools Protocol `Network.responseReceived`, four calls per gateway:

| gateway | protocol | connectionId | connectionReused |
| --- | --- | ---: | --- |
| zjs.zec.rocks (66.241.125.16) | h2 | 30, 30, 30, 30 | false, **true, true, true** |
| chainsafe.dev (18.118.79.248) | h2 | 60, 60, 60, 60 | false, **true, true, true** |

`tonic-web-wasm-client` issues one `fetch` per gRPC call, but the browser pools those onto
a single HTTP/2 connection per origin. Only the first call of a session pays DNS + TCP +
TLS, which shows up as the ~125 ms extra on the first row of every five-run sample above.
So "a new connection per call" is not where the time goes, and nothing here needs fixing.

## 3. Streaming throughput

The real spans matter, not 60 blocks. The M1/fee envelope sits at block **3,490,472** and
the tip today is **3,491,249**: a **777-block** span, which is what both the open scan and
the anchor walk cover.

800 compact blocks from the browser, three runs each:

| gateway | shape | wall | bytes |
| --- | --- | ---: | ---: |
| zjs.zec.rocks | one stream | 1,228 / 1,024 / **445** ms | 5,707,574 |
| zjs.zec.rocks | 4 concurrent chunks | 694 / 439 / **360** ms | 5,707,679 |
| chainsafe.dev | one stream | 1,069 / — / **380** ms | 5,707,560 |
| chainsafe.dev | 4 concurrent chunks | 314 / 534 / **418** ms | 5,707,623 |

5.7 MB in 0.4–1.2 s: **4.7–14 MB/s**, and one stream already saturates most of it.
Chunking into four buys a few hundred milliseconds at best.

(One of the chainsafe single-stream runs came back with zero messages and 63 bytes — a
gRPC error frame — inside 113 ms. Roughly a 1-in-15 failure, silent, and the old code would
have surfaced it as a whole failed scan. See §7.)

## 4. So where do the 25.8 s go?

Add it up for the 777-block open scan on this host:

| | |
| --- | ---: |
| gateway choice + chain tip (one unary call) | ~0.11 s |
| the block-range stream, 5.5 MB of compact blocks | ~0.5–1.2 s |
| `GetTransaction` for the hit | ~0.11 s |
| **total network** | **~0.8–1.4 s** |
| measured open/scan | **25.8 s** |
| **left over: wasm** | **~24.5 s, ≈ 96%** |

The leftover is protobuf decoding plus trial decryption: every Ironwood and Orchard action
in every one of 777 blocks, against two incoming viewing keys, single-threaded. The witness
stage's 28.4 s is the same span again — the same stream, plus a Sinsemilla hash per
commitment as the Ironwood frontier is replayed forward to the anchor.

This also explains the regression exactly, and it is not a regression at all: **the
envelope aged**. M4's 2–3 s open and 7 s witness were measured hours after the envelope was
funded, over a few dozen blocks. It is now 777 blocks old, and 777/35 ≈ 22 — the same ratio
as 25.8 s / 1.2 s. Nothing got slower; there is simply ~22x more chain to read.

**Consequence: none of (a)–(d) can make today's open much faster.** The whole network path
is 1.4 s out of 25.8 s. What they *can* do is stop a stalled or erroring gateway from
turning 25.8 s into a minute or a failure, which §1 and §3 show is a real and silent risk.
That is what was implemented.

## 5. What was implemented

In payoff order, given the above.

**(a) Gateway race at the start of a session.** `crates/core/src/gateway.rs::choose` sends
`GetLatestBlock` to every configured gateway at once and keeps the first that answers,
inside a 1.5 s budget. It is **free**: the answer *is* the chain tip the caller needed, so
the old separate `GetLatestBlock` is gone. The winner leads the session and is reported to
JS as `gateway` on both `OpenResult` and `SweepResult`, and shown on the Done screen's
device line: `… · gateway zjs.zec.rocks`. A race nobody wins is not an error — both
gateways being slow is not both being broken — so the preferred one leads and (c) takes
over. Every gateway *refusing* is an error, as it always was.

**(b) Independent fetches in parallel.** The witness path used to make, in order:
`GetLatestBlock`, one `GetTransaction` per distinct funding transaction, `GetTreeState(h-1)`
and `GetBlock(h)` — four or more serial round trips, each ~110 ms, before the anchor walk
could start. Every one of those is independent of the others, and both bounds of the walk
come out of the request rather than off the wire, so they now go out together
(`try_join4`). After the walk, the per-note-block root checks and the anchor's tree state
are likewise one batch instead of one call each. The open path fetches the full
transactions of all hits concurrently. Measured saving: ~0.4–0.6 s, and it grows with the
number of notes.

**(c) Per-call header deadline with retry on the other gateway.** `gateway::Failover` is a
`tower` service wrapping the gateways in preference order. Each call gets 6 s to produce
*response headers*; a miss, or an outright refusal, re-sends the identical request to the
next gateway. Headers are the right deadline because that is where a stalled gateway shows
up and the only point at which a retry is free — nothing has reached the caller yet.
`SendTransaction` is excluded: it is the one call with a side effect, and this code will not
create a double-spend attempt. This replaces the old JS-level failover, which could only
fire after a whole scan had already thrown.

**(d) Chunked concurrent block ranges: not done, deliberately.** §3 measures the whole
777-block range at 0.4–1.2 s and four concurrent chunks at 0.36–0.7 s. Buying ~0.4 s at the
cost of reordering the compact-block stream — which the scan consumes in order, and which
the witness replay *must* consume in order, because an Ironwood frontier is built by
appending commitments in chain order — is a bad trade against a 25 s workload. It would be
the right change if the network were the bottleneck. It is not.

Every correctness check is untouched: the replayed Ironwood root is still compared against
the server's tree state at every note block, the anchor root is still the server's, the
notes are still re-derived from the secret rather than trusted, and the same-note-twice
guard still runs before any network work.

## 7. What this leaves on the table

- **The real 25 s is single-threaded wasm scanning.** The lever is the scan itself:
  `pool_types` on `GetBlockRange` (asking for the Ironwood set alone instead of the whole
  legacy shielded set), or putting trial decryption through the same rayon pool M4 built
  for proving. Both are bigger changes than this one and neither is a network change.
  **The rayon half of that is done; see §8.** `pool_types` is still open.
- **A mid-stream stall is still not covered.** The header deadline cannot see a gateway
  that answers promptly and then dribbles. Covering that means a stream-level watchdog and
  a resumable scan.
- **A silent `GetBlockRange` error frame** (§3) now costs one retry on the other gateway
  rather than a failed scan, but nothing counts how often it happens.

## 8. Taking the two levers §7 named: threads on the scan, a cap on the walk

Two changes, both aimed at the 96% that §4 showed is wasm and not wire.

**(e) The compact pass runs on the rayon pool.** Blocks are buffered in chunks of 64 as
they come off the *same single* `GetBlockRange` stream, and each chunk goes through
`par_iter` in `crates/core/src/scan.rs`. The parallel path is behind
`#[cfg(feature = "multicore")]`, so the stable single-threaded package compiles the loop it
always had; only the `core-mt` package is threaded. The answers are identical either way —
rayon's `collect` keeps source order, and within a block the hits are pushed in `vtx`
order — which matters because the frontier replay reads the chain in order. Two cheap
skips went in alongside: a block with no Orchard-family action is skipped without
allocating, and each pool is skipped per transaction when it has no actions. Sapling
outputs are never trial-decrypted at all; an envelope address has one Orchard receiver, so
there is no Sapling note to find.

**(f) The witness walk is capped.** `anchor = min(tip, newest note height + 120)`, where
it used to be "walk to the tip if the envelope is inside 1,500 blocks, else anchor in the
note's own block". 120 blocks is about two and a half hours of mainnet. It is a
privacy/latency trade-off and not a correctness one — any finalized tree state's root is a
valid anchor — and it is written up in DECISIONS.md D18 and crates/core/README.md. The
root assertion is untouched: the replayed root is still compared against the server's
`GetTreeState` at every note block, and the anchor root is still the server's own.

### What §8 leaves on the table

- **Most of the remaining witness time is not the walk.** The same spec's stage log puts
  the whole witness stage at **6.1 s** on a bare page, against 17.6-19.0 s through the
  product, for the same 120-block replay. So roughly 12 s of the product's witness stage is
  something other than replaying blocks, and nothing here measured what. That is the next
  thing to profile, and it is now a bigger share of a sweep than the walk is.
- **`pool_types` on `GetBlockRange` is still open** (§7). Asking the server for the
  Ironwood set alone would cut both the bytes and the actions to trial-decrypt, and it
  composes with the threads rather than competing with them.
- **A phone has 2 threads, not 4** (D17). The 2.8x here is a desktop figure; the phone's
  scan will gain less, and the cap on the walk is worth proportionally more there.

## 9. The 12 seconds §8 could not account for

§8 ended on an open question: the witness stage measured **6.1 s** driving the wasm
directly from a bare page and **17.6–19.0 s** through the product, for what looked like
the same 120-block replay, and nothing had measured the difference. This section
measures it. **It is not a gap.** The 6.1 s and the 18 s are two different 120-block
windows of mainnet carrying very different numbers of note commitments, and the whole of
the product's witness stage is one thing: Sinsemilla hashing, done twice.

### How it was measured

`crates/core/src/sweep.rs` now times each phase of the witness stage with `js_sys::Date::now()`
(`now_ms()`, which falls back to `SystemTime` for the native test) and reports each one
through the `on_stage` callback it already had. Only the **first** report of a stage sets
a timestamp in the UI (`markStage`), so the extra lines change no measurement — they are
the stage's own detail line, and they cross to the page as ordinary stage messages, each
stamped in the worker as it is posted and again on the main thread as it arrives.

One dry run of the fee envelope, four threads, `?dry=1`, production build on
`ZENVELOPE_E2E_PORT=4241`, Playwright's own chromium on this droplet. **Nothing was
broadcast.**

| witness phase | before |
| --- | ---: |
| worker receives the tap → core's first report (gateway race) | 0.11 s |
| `GetTransaction` + `GetTreeState(h-1)` + `GetBlock(h)`, concurrent | 0.27 s |
| re-deriving the note from the secret | 0.10 s |
| appending the note's own block | 0.15 s |
| `GetBlockRange` response headers | 0.11 s |
| **replaying 120 blocks** | **19.36 s** |
| — of which waiting for blocks to arrive | 0.05 s |
| — of which `WitnessScan::append_block` | **19.29 s** |
| checking the replayed roots against the chain (2 `GetTreeState`) | 0.20 s |
| `WitnessScan::finish` | 0.14 s |
| **witness stage, total** | **20.32 s** |

**The network is 0.7 s of a 20 s stage.** Every candidate the question listed is ruled
out by this table: there is no re-scan from the birthday (the note is re-derived from one
`GetTransaction`, 0.25 s), no serial await chain in JS (the tap reaches the worker in
1 ms and the core's first report follows 110 ms later), no second `GetBlockRange` of the
*witness* range, and the proving-key warm-up had finished 0.2 s before the tap — this
harness waits for "Keys ready", and the arithmetic says so independently: witness 19.0 s
plus proving 13.7 s is §8's whole 33.0 s tap-to-Done, leaving nothing unaccounted for
before the witness stage.

What is left is 19.29 s of `append_block` over **10,820 commitments**: 1.78 ms each.

### Why it was twice what it needed to be

`WitnessScan` held two things and appended every commitment to both:

- a `CommitmentTree`, whose root is compared against the server's `GetTreeState` at each
  note block and at the anchor, and
- one `IncrementalWitness` per note, cut from that tree as the replay passes the note's
  own commitment.

An `IncrementalWitness` carries its **own** copy of the frontier and keeps it current as
leaves arrive — that is what lets it produce an auth path and a root at the end. So from
the moment the last witness has been taken, the tree and the witness are hashing the same
commitments into the same root, on the same thread, and the tree's answer is the one
nothing reads: `tree_root_hex()` and `finish()` can take the root off a witness instead
and get the identical string.

For this envelope the note is in the **first** block of the walk, so 10,820 of the 10,820
commitments were hashed twice.

### The fix

`WitnessScan` now counts the slots still waiting for a commitment. At zero — and only
when the scan has at least one slot — it is **sealed**: the `CommitmentTree` stops being
appended to, and both `tree_root_hex()` and `finish()` read the root off a witness.

**Every root assertion is exactly where it was.** The replayed root is still compared
against the server's `GetTreeState` at every note block and at the anchor, each note's
witness root is still compared against the server's, and a mismatch is still a hard
failure with no fallback. What changed is which of two identical values is computed —
not whether the chain agrees with it. The tree is still the thing every witness is cut
from, so it still has to be current up to the last note; a sweep with no notes is refused
long before this code runs, and a scan opened with no slots is never sealed.

Two smaller things went with it:

- **The sweep no longer asks for the chain tip twice.** `gateway::choose` *is* a
  `GetLatestBlock` and already holds the answer; `sweep()` was issuing a second one
  inside the witness batch. It now takes `known_tip: Option<u32>` and the browser hands
  the race's answer in. One round trip, and one fewer call that can fail — during this
  work that very call came back `malformed response` from a healthy gateway and failed a
  whole sweep.
- **The Timing block gained a "waiting for keys" row.** The core worker holds one wasm
  module and `warm_proving_key` is one long call with no `await` in it, so a recipient
  who taps "Send it on" before the key is ready waits for the rest of that build before
  the core reads a byte. That wait falls **between** the tap and the first stage the core
  reports, so it never inflated the witness row — it inflated nothing at all, and only
  "total tap-to-done" moved. It has its own line now, a measured `0.0 s` when the key was
  already warm, and the progress screen says "Finishing the keys this sweep needs…"
  instead of "Starting…" while it is happening.

### What §9 leaves on the table

- **The remaining 9 s is still one Sinsemilla chain over 10,820 commitments.** Halving it
  again means either fewer commitments (a smaller [`ANCHOR_WALK_CAP`] — a privacy
  trade-off, D18, not a speed-up to take quietly) or a faster hash. Nothing about it is
  parallel: each leaf's carry depends on the last.
- **The witness re-streams blocks the open scan already read.** The open scan covers
  birthday→tip, which contains the whole `note+1..anchor` walk; the witness asks for those
  120 blocks again. Measured here at 0.11 s of headers and 0.05–0.34 s of waiting, because
  the bytes are small next to the hashing — keeping 120 blocks alive across two calls to
  buy a tenth of a second is the wrong trade today. It becomes the right one if the
  hashing ever stops dominating.
- **A gateway can still answer a healthy-looking call with a truncated body.** One run
  during this work got `malformed response` from `GetLatestBlock` — the redundant one,
  now gone — and it failed a whole sweep, while `Failover`'s retry never fired because
  the headers had arrived. §7's "mid-stream stall" gap, seen in the wild.
- **`pool_types` on `GetBlockRange` is still open** (§7), and it would help the witness
  walk as well as the open scan: an Ironwood-only range is fewer bytes to decode, though
  not fewer commitments to hash.

## 10. The last lever §9 named: the cap itself, 120 blocks → 24

§9 ended with the witness stage at 9.7 s and one thing left in it: 10,820 commitments
hashed once each, at about 0.8 ms apiece, because the walk is 120 blocks long. That
length was never a correctness requirement, so this section shortens it.

**`ANCHOR_WALK_CAP` is now 24 blocks**, about half an hour of mainnet at 75 s per block.
The rule is unchanged — `anchor = min(tip, newest note height + cap)` — and so is every
root assertion: the replayed root is still compared against the server's `GetTreeState`
at every note block and at the anchor, and a mismatch is still a hard failure with no
fallback.

**Why 24 is as valid as 120.** Zebra accepts a spend against the root of any finalized
Ironwood tree state, and the M3 spike verified a **same-block** anchor against mainnet —
the extreme case of the same thing. So no cap, of any size, can build a transaction the
chain will not take. The walk exists for one reason only: so the anchor does not pin the
exact funding block. Any distance past the note buys that, and every block of it is paid
for in Sinsemilla hashing on the recipient's device. 24 blocks is the smallest distance
that still buys it comfortably, and the cost side of D18 is what this section measures.

### Measured

Same droplet, same envelope, same method as §9: `./scripts/build-core.sh` (both
packages), `npm run build`, `vite preview` on `ZENVELOPE_E2E_PORT=4251`, Playwright's own
chromium, `?dry=1`, the fee envelope from the private M3-DEST.md (0.0003 ZEC).
**Nothing was broadcast**: every run took the dry path and the done screen's "Dry run:
transaction built and proved, not sent" was asserted on the way out.

| | witness | open/scan | proving | tap to Done |
| --- | ---: | ---: | ---: | ---: |
| **before** (§9, cap 120, median of 3) | **9.7 s** | 11.9 s | 13.1 s | 23.0 s |
| after, cap 24, run 1 | 1.5 s | 16.0 s | 14.1 s | 15.8 s |
| after, cap 24, run 2 | 1.3 s | 12.0 s | 15.3 s | 16.8 s |
| **after, cap 24** | **1.3–1.5 s** | 12.0–16.0 s | 14.1–15.3 s | **15.8–16.8 s** |

Device line, both runs: `proving: 4 threads · hardwareConcurrency 8 · Chrome on Linux`,
gateway `zjs.zec.rocks`. Open/scan and proving are untouched by this change and move only
with the chain's length and the droplet's load.

The witness stage's own detail line, from a third instrumented dry run on the same build:

| witness phase | cap 120 (§9) | cap 24 |
| --- | ---: | ---: |
| fetch: `GetTransaction` + `GetTreeState(h−1)` + `GetBlock(h)` | 0.27 s | 0.28 s |
| **replaying the walk** | **120 blocks** | **24 blocks** |
| — commitments hashed | 10,820 | **648** |
| — `WitnessScan::append_block` | 8.8 s | **0.57 s** |
| — waiting for blocks to arrive | 0.05–0.34 s | 0.09 s |
| checking the replayed roots against the chain | 0.20 s | 0.18 s |
| **witness stage, total** | **9.7 s** | **1.5 s** |

**The cap was verified on mainnet, not just in the unit tests.** The same instrumented
run reports `anchor … at height 3491080` for a note at 3,491,056 — exactly `note + 24`,
where §9's run on the same note anchored at 3,491,176, exactly `note + 120` — and the
proof built on it passed `WitnessScan::finish`'s root check against the server's own tree
state.

Both walks start at the same block, so the 648 are literally the first 24 blocks' worth
of the 10,820: this stretch of chain happens to be sparse, at 27 commitments per block
against the 90 the full 120-block window averages. A denser 24 blocks costs more — about
**2 s** at that 90-per-block average on this desktop, which is the figure the const doc
and crates/core/README.md quote, against about **10 s** for 120 blocks. The walk is one
sequential Sinsemilla chain either way, so a recent phone's two cores (D17) do not change
its shape; its faster per-hash rate puts the same 24 blocks under a second there, where
120 would have been the dominant wait of the whole sweep. No phone was measured here.

### What §10 leaves on the table

- **The anchor is now `note + 24` for anything older than half an hour.** That is the
  privacy side of D18 moving, not the speed side: an observer reading an old envelope's
  anchor learns a 24-block window rather than a 120-block one. It is still not the
  funding block, which is the property the walk is for.
- **The witness stage is no longer worth profiling.** At 1.5 s of a 16 s sweep, the whole
  of it is smaller than the run-to-run spread of proving. Everything left is the proof
  and the open scan.
- **`pool_types` on `GetBlockRange` is still open** (§7, §9), and the case for it is now
  entirely the open scan's: 24 blocks of witness range is not worth an optimization.
