# Where the open and the witness actually spend their time

2026-09-21. Today's live runs on this host showed **open/scan 25.8 s** and **witness
28.4 s**, against 2–3 s and 7 s in [M4-VERIFICATION.md](M4-VERIFICATION.md). The obvious
reading — "the gRPC-web gateways got slow and variable" — is measured here, and it is
**wrong**. The network is about **4%** of that time. The rest is the wasm doing arithmetic
on 777 more blocks than it used to.

Everything below was measured from this droplet (DigitalOcean, Linux) and from Playwright's
own chromium on the same droplet, against both gateways, five runs each, at two different
minutes. The harness speaks grpc-web by hand (5-byte frame headers over `fetch`) so that
what is timed is the wire and nothing else.

## 2. Is there a TLS handshake per call?

No. Chrome DevTools Protocol `Network.responseReceived`, four calls per gateway:

| gateway | protocol | connectionId | connectionReused |
| --- | --- | ---: | --- |
| zjs.zec.rocks (66.241.125.16) | h2 | 30, 30, 30, 30 | false, **true, true, true** |
| chainsafe.dev (18.118.79.248) | h2 | 60, 60, 60, 60 | false, **true, true, true** |

`tonic-web-wasm-client` issues one `fetch` per gRPC call, but the browser pools those onto
a single HTTP/2 connection per origin. Only the first call of a session pays DNS + TCP +
TLS, which shows up as the ~125 ms extra on the first row of every five-run sample above.
So "a new connection per call" is not where the time goes, and nothing here needs fixing.

## 3. Streaming throughput

The real spans matter, not 60 blocks. The M1/fee envelope sits at block **3,490,472** and
the tip today is **3,491,249**: a **777-block** span, which is what both the open scan and
the anchor walk cover.

800 compact blocks from the browser, three runs each:

| gateway | shape | wall | bytes |
| --- | --- | ---: | ---: |
| zjs.zec.rocks | one stream | 1,228 / 1,024 / **445** ms | 5,707,574 |
| zjs.zec.rocks | 4 concurrent chunks | 694 / 439 / **360** ms | 5,707,679 |
| chainsafe.dev | one stream | 1,069 / — / **380** ms | 5,707,560 |
| chainsafe.dev | 4 concurrent chunks | 314 / 534 / **418** ms | 5,707,623 |

5.7 MB in 0.4–1.2 s: **4.7–14 MB/s**, and one stream already saturates most of it.
Chunking into four buys a few hundred milliseconds at best.

(One of the chainsafe single-stream runs came back with zero messages and 63 bytes — a
gRPC error frame — inside 113 ms. Roughly a 1-in-15 failure, silent, and the old code would
have surfaced it as a whole failed scan. See §7.)

## 4. So where do the 25.8 s go?

Add it up for the 777-block open scan on this host:

| | |
| --- | ---: |
| gateway choice + chain tip (one unary call) | ~0.11 s |
| the block-range stream, 5.5 MB of compact blocks | ~0.5–1.2 s |
| `GetTransaction` for the hit | ~0.11 s |
| **total network** | **~0.8–1.4 s** |
| measured open/scan | **25.8 s** |
| **left over: wasm** | **~24.5 s, ≈ 96%** |

The leftover is protobuf decoding plus trial decryption: every Ironwood and Orchard action
in every one of 777 blocks, against two incoming viewing keys, single-threaded. The witness
stage's 28.4 s is the same span again — the same stream, plus a Sinsemilla hash per
commitment as the Ironwood frontier is replayed forward to the anchor.

This also explains the regression exactly, and it is not a regression at all: **the
envelope aged**. M4's 2–3 s open and 7 s witness were measured hours after the envelope was
funded, over a few dozen blocks. It is now 777 blocks old, and 777/35 ≈ 22 — the same ratio
as 25.8 s / 1.2 s. Nothing got slower; there is simply ~22x more chain to read.

**Consequence: none of (a)–(d) can make today's open much faster.** The whole network path
is 1.4 s out of 25.8 s. What they *can* do is stop a stalled or erroring gateway from
turning 25.8 s into a minute or a failure, which §1 and §3 show is a real and silent risk.
That is what was implemented.

## 5. What was implemented

In payoff order, given the above.

**(a) Gateway race at the start of a session.** `crates/core/src/gateway.rs::choose` sends
`GetLatestBlock` to every configured gateway at once and keeps the first that answers,
inside a 1.5 s budget. It is **free**: the answer *is* the chain tip the caller needed, so
the old separate `GetLatestBlock` is gone. The winner leads the session and is reported to
JS as `gateway` on both `OpenResult` and `SweepResult`, and shown on the Done screen's
device line: `… · gateway zjs.zec.rocks`. A race nobody wins is not an error — both
gateways being slow is not both being broken — so the preferred one leads and (c) takes
over. Every gateway *refusing* is an error, as it always was.

**(b) Independent fetches in parallel.** The witness path used to make, in order:
`GetLatestBlock`, one `GetTransaction` per distinct funding transaction, `GetTreeState(h-1)`
and `GetBlock(h)` — four or more serial round trips, each ~110 ms, before the anchor walk
could start. Every one of those is independent of the others, and both bounds of the walk
come out of the request rather than off the wire, so they now go out together
(`try_join4`). After the walk, the per-note-block root checks and the anchor's tree state
are likewise one batch instead of one call each. The open path fetches the full
transactions of all hits concurrently. Measured saving: ~0.4–0.6 s, and it grows with the
number of notes.

**(c) Per-call header deadline with retry on the other gateway.** `gateway::Failover` is a
`tower` service wrapping the gateways in preference order. Each call gets 6 s to produce
*response headers*; a miss, or an outright refusal, re-sends the identical request to the
next gateway. Headers are the right deadline because that is where a stalled gateway shows
up and the only point at which a retry is free — nothing has reached the caller yet.
`SendTransaction` is excluded: it is the one call with a side effect, and this code will not
create a double-spend attempt. This replaces the old JS-level failover, which could only
fire after a whole scan had already thrown.

**(d) Chunked concurrent block ranges: not done, deliberately.** §3 measures the whole
777-block range at 0.4–1.2 s and four concurrent chunks at 0.36–0.7 s. Buying ~0.4 s at the
cost of reordering the compact-block stream — which the scan consumes in order, and which
the witness replay *must* consume in order, because an Ironwood frontier is built by
appending commitments in chain order — is a bad trade against a 25 s workload. It would be
the right change if the network were the bottleneck. It is not.

Every correctness check is untouched: the replayed Ironwood root is still compared against
the server's tree state at every note block, the anchor root is still the server's, the
notes are still re-derived from the secret rather than trusted, and the same-note-twice
guard still runs before any network work.

## 6. Before and after, on the real envelope

Three dry runs each, Playwright's own chromium, `?dry=1`, `ZENVELOPE_E2E_PORT=4221`, the
fee envelope from the private M3-DEST.md (0.0003 ZEC, note at block 3,490,472), four
proving threads. **Nothing was broadcast**: every run took the dry path and the done
screen's "not sent" copy was asserted on the way out.

| | open/scan | witness | proving | tap to Done |
| --- | ---: | ---: | ---: | ---: |
| before, today's live run | 25.8 s | 28.4 s | 13.8 s | — |
| after, run 1 | 28.0 s | 30.2 s | 13.0 s | 43.5 s |
| after, run 2 | 28.4 s | 34.1 s | 15.1 s | 49.5 s |
| after, run 3 | 28.6 s | 32.0 s | 14.6 s | 46.8 s |
| **after, median** | **28.4 s** | **32.0 s** | **14.6 s** | **46.8 s** |

Device line, all three: `proving: 4 threads · hardwareConcurrency 8 · Chrome on Linux ·
gateway zjs.zec.rocks` — the last field is new, and is what the race settled on.

**Read this as flat, not as a regression.** The two sets were taken hours apart and the
span grew underneath them: mainnet made ~120 blocks between the before run and these, so
the same work covers ~15% more chain. 25.8 s scaled by that is ~29.7 s, which is where
these land. The ~0.5 s of round trips (a)–(c) removed is well inside that drift, exactly as
§4 predicts: **the network was never the 25 s, so removing network time could not move the
number.** What changed is the failure behaviour, which no timing table shows — a stalled or
erroring gateway now costs one retry instead of the session.

## 7. What this leaves on the table

- **The real 25 s is single-threaded wasm scanning.** The lever is the scan itself:
  `pool_types` on `GetBlockRange` (asking for the Ironwood set alone instead of the whole
  legacy shielded set), or putting trial decryption through the same rayon pool M4 built
  for proving. Both are bigger changes than this one and neither is a network change.
  **The rayon half of that is done; see §8.** `pool_types` is still open.
- **A mid-stream stall is still not covered.** The header deadline cannot see a gateway
  that answers promptly and then dribbles. Covering that means a stream-level watchdog and
  a resumable scan.
- **A silent `GetBlockRange` error frame** (§3) now costs one retry on the other gateway
  rather than a failed scan, but nothing counts how often it happens.

## 8. Taking the two levers §7 named: threads on the scan, a cap on the walk

Two changes, both aimed at the 96% that §4 showed is wasm and not wire.

**(e) The compact pass runs on the rayon pool.** Blocks are buffered in chunks of 64 as
they come off the *same single* `GetBlockRange` stream, and each chunk goes through
`par_iter` in `crates/core/src/scan.rs`. The parallel path is behind
`#[cfg(feature = "multicore")]`, so the stable single-threaded package compiles the loop it
always had; only the `core-mt` package is threaded. The answers are identical either way —
rayon's `collect` keeps source order, and within a block the hits are pushed in `vtx`
order — which matters because the frontier replay reads the chain in order. Two cheap
skips went in alongside: a block with no Orchard-family action is skipped without
allocating, and each pool is skipped per transaction when it has no actions. Sapling
outputs are never trial-decrypted at all; an envelope address has one Orchard receiver, so
there is no Sapling note to find.

**(f) The witness walk is capped.** `anchor = min(tip, newest note height + 120)`, where
it used to be "walk to the tip if the envelope is inside 1,500 blocks, else anchor in the
note's own block". 120 blocks is about two and a half hours of mainnet. It is a
privacy/latency trade-off and not a correctness one — any finalized tree state's root is a
valid anchor — and it is written up in DECISIONS.md D18 and crates/core/README.md. The
root assertion is untouched: the replayed root is still compared against the server's
`GetTreeState` at every note block, and the anchor root is still the server's own.

Device line, all six: `hardwareConcurrency 8 · Chrome on Linux`, gateway `zjs.zec.rocks`
or `zcash-mainnet.chainsafe.dev` as the race settled it.

**Open/scan: 26.4 s → 9.3 s, a 2.8x speed-up on four threads.** That is the one number
this section is about, and it is measured on the same span within a few blocks, minutes
apart, so it is not the drift §6 had to argue around. 2.8x rather than 4x is the shape you
expect: the stream, the protobuf decode and the `BTreeSet` of hits are still on one thread,
and Amdahl takes the rest.

Against §6's before, which was the same envelope at ~790 blocks: 28.4 s → 26.4 s
single-threaded on ~830 blocks. That ~10% is the cheap skips, measured across a 5% larger
span; it is small because the blocks that get skipped are the ones that were cheap anyway.

**Witness: 32.0 s → 17.6/19.0 s, and it no longer grows with the envelope's age.** Both
packages agree, which is the expected answer: the replay is sequential and was deliberately
left that way (an Ironwood frontier is built by appending in chain order, so there is no
independent unit of work in it). The anchor the sweep actually used was verified on
mainnet: `e2e/m3-core.spec.ts` reports **anchor 3,490,592** for a note at 3,490,472 —
exactly `note + 120` — and the proof built on it passed `WitnessScan::finish`'s root check
against the server's own tree state.

### What §8 leaves on the table

- **Most of the remaining witness time is not the walk.** The same spec's stage log puts
  the whole witness stage at **6.1 s** on a bare page, against 17.6-19.0 s through the
  product, for the same 120-block replay. So roughly 12 s of the product's witness stage is
  something other than replaying blocks, and nothing here measured what. That is the next
  thing to profile, and it is now a bigger share of a sweep than the walk is.
- **`pool_types` on `GetBlockRange` is still open** (§7). Asking the server for the
  Ironwood set alone would cut both the bytes and the actions to trial-decrypt, and it
  composes with the threads rather than competing with them.
- **A phone has 2 threads, not 4** (D17). The 2.8x here is a desktop figure; the phone's
  scan will gain less, and the cap on the walk is worth proportionally more there.
